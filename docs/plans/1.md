# Устранение повторных запросов пароля `sudo`

Сейчас `piburn` выполняет интерактивный `sudo -v` перед каждой привилегированной стадией. Поскольку запись и проверка карты длятся значительно дольше стандартного пятиминутного срока действия sudo-ticket, пароль запрашивается снова. Проблема решаема: приложение будет один раз авторизовываться, а затем периодически и неинтерактивно продлевать ticket через `sudo -n -v`.

## Изменения реализации

- Добавить внутренний объект сессии `sudo`, общий для всего запуска `piburn` и всех обрабатываемых карт.
- При запуске сессии один раз выполнить интерактивный `sudo -v` и запомнить по монотонным часам срок следующего продления.
- Не чаще одного раза в 60 секунд выполнять `sudo -n -v`:
  - перед запуском каждой привилегированной стадии;
  - внутри циклов записи и чтения после обработки очередного блока;
  - во время ожидания или интерактивного выбора следующей карты.
- Не использовать фоновый Python-поток: существующие процессы `dd` создаются с `preexec_fn`, сочетание которого с потоками небезопасно. Продление будет кооперативным — из уже существующих циклов обработки и ожидания.
- Если неинтерактивное продление неожиданно не сработало, выполнить контролируемую повторную авторизацию через `sudo -v`. В нормальном непрерывном запуске этого происходить не должно, но это позволит продолжить работу после принудительного сброса ticket или длительной приостановки процесса.
- Передавать одну и ту же sudo-сессию в проверку носителя, запись образа и сверку. Для интерактивного селектора и ожидания устройства добавить необязательный callback периодического обслуживания.
- Если повторная авторизация завершилась ошибкой во время активной операции, корректно остановить группу процессов `sudo`/`dd`, дождаться её завершения, извлечь карту существующим аварийным путём и показать `BurnError`.
- Сохранить `sudo -n dd`, проверки fingerprint карты и текущую изоляцию групп процессов без изменений.
- Не хранить пароль, не менять `/etc/sudoers`, не увеличивать системный `timestamp_timeout` и не выполнять `sudo -k`, чтобы не сбрасывать ticket, созданный пользователем до запуска `piburn`.
- Уточнить пользовательское сообщение и README: обычно пароль запрашивается один раз; повторный запрос возможен только при аннулировании или нестандартно коротком сроке действия ticket.

## Интерфейсы

- Публичные CLI-параметры и формат конфигурации не меняются.
- Внутренние функции длительного чтения/записи получат sudo-сессию, а функции ожидания и выбора устройства — необязательный heartbeat-callback.
- Интервал продления задаётся внутренней константой `60` секунд.
- Hypothesis не требуется: поведение представляет собой небольшую детерминированную машину состояний, которую надёжнее проверять управляемыми монотонными часами и mock-процессами.

## Тесты

|---|---|---|---|---|
| `test_sudo_session_authenticates_once_and_sets_refresh_deadline` | Создание sudo-сессии выполняет одну первоначальную интерактивную авторизацию | Убедиться, что источник обычного повторного запроса устранён | Подменить subprocess-хелпер и монотонные часы; создать сессию при заранее известном времени | Ровно один вызов `sudo -v`; он интерактивный; следующий срок продления равен текущему времени плюс 60 секунд |
| `test_sudo_session_does_not_refresh_before_deadline` | Частые heartbeat-вызовы до дедлайна ничего не запускают | Не создавать лишние процессы `sudo` на каждом блоке данных | Авторизовать сессию, затем несколько раз передвинуть поддельные часы внутри 60-секундного интервала | После начальной авторизации дополнительных вызовов `sudo` нет; дедлайн не меняется |

## Проверка результата

- Запустить полный `pytest` с branch coverage, затем `ruff check piburn tests` и `mypy`.
- Проверить совместимость с минимальной поддерживаемой Python 3.8: не использовать `subprocess.Popen(process_group=...)` и другие более новые API.
- Критерий успеха: при непрерывном запуске длительностью больше пяти минут пароль вводится один раз, а все последующие привилегированные стадии проходят через действующий sudo-ticket.
